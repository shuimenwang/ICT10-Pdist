## 1. 这场比赛在打什么

**赛事背景（第十届，2025-2026）**：

- 华为 ICT 大赛挑战赛第二次举办，主题合并为「超智融合」单一赛道：超算基准优化、并行调优、AI 算子加速、大模型推理效率一个赛道全考。
- 赛题明确包含 CANN 算子题 + 昇腾推理优化题 + xLLM 推理引擎专项题；硬件底座是昇腾 910B。
- 平行的「算子赛」（昇腾 AI 算子开发赛道）走同一条技术路线：Ascend C + CANN，资格赛刷两项微认证，决赛发算子赛题，全球总决赛比性能调优 + 现场答辩。

**为什么从 Pdist 练起**：单算子开发是两大赛道共同的「基本功考题」——它把精度调试、数据切分、多核并行、性能调优四件事压缩在一个算子里。练透它，大题只剩工程量。

## 2. Pdist 到底算个啥

类比：**全班同学两两距离表**。输入 N 个「同学」（每人是一个 M 维特征向量），输出 N×(N−1)/2 个两两距离。

$$d(x, y) = \left( \sum_{i=1}^{M} |x_i - y_i|^p \right)^{1/p}$$

p 决定「距离的口味」：

| p 值 | 名字 | 直觉 |
|---|---|---|
| p=2 | 欧氏距离 | 两点间直线距离（默认值） |
| p=1 | 曼哈顿距离 | 出租车在格子街道里走的距离 |
| p=0 | 特殊分支 | 数一数有多少个维度不一样 |
| 其他 p | 闵可夫斯基距离 | 通用幂平均，走 ln+exp 通路 |

输入输出：单输入张量 X（N 行），输出 Y（N·(N−1)/2 个距离），p 默认 2.0，无广播逻辑——**赛题把复杂度全压在「算得对 + 算得快」上**。

## 3. 昇腾 AI Core 世界观：大仓库与小厨房

| 概念 | 类比 | 特点 |
|---|---|---|
| GM（Global Memory） | 外挂 SDRAM / 大仓库 | GB 级容量，进出慢 |
| UB（Unified Buffer） | 片上 SRAM / 小厨房 | 百 KB 级，快一个数量级 |
| 向量指令（vec_xxx） | 硬件 SIMD | 比标量循环快一个数量级 |
| 多 AI Core | 多个厨房同时开火 | 要分活均匀 + 最后汇总 |

三条铁律：

1. **菜必须进厨房才能炒**：数据必须 GM→UB 搬入后才能参与向量计算，算完再搬回 GM。
2. **厨房很小**：一行数据装不下就得切块（Tiling），这是所有问题的根源，也是所有优化的起点。
3. **搬运和炒菜要同时进行**：Double Buffering 乒乓缓存——一块缓冲区搬运时另一块计算，避免计算单元等米下锅。

写过 STM32 / 驱动的话：写内核 ≈ 驱动 + SIMD 汇编 + 多线程归约的合体。

## 4. 初赛核心考点：四大切分场景（Tiling）

Tiling =「一块肉怎么切才塞得进小厨房」的策略，Host 侧决定、Kernel 侧执行：

| 场景 | 处理方式 | 易错点 |
|---|---|---|
| ① 整行放得下 UB | 单轮循环算完 | 无（基线场景） |
| ② 一行放不下 UB | 拆多轮循环，核内累加中间结果 | 累加变量没清零 / 轮次边界算错 |
| ③ 数据量超大 | 多核并行切分 | 负载不均（单核扛尾巴）；各核写回冲突 |
| ④ 非 32B 对齐 | Pad 补齐 + Mask 过滤无效值 | Pad 长度算错 → UB 越界；Mask 漏加 → 脏数据混入 |

为什么 32 字节对齐是硬约束：硬件内存总线按 32B 粒度取数，未对齐访问直接报错（类比 cacheline 对齐）。

**超大 shift 值（如 133177）** 是训练营故意给的「折磨场景」：同时触发 ②③④。

## 5. 硬件没有幂指令怎么办：ln + exp 变换

昇腾向量单元没有直接的 `x^p` 指令，用数学变换绕：

```text
|x|^p              = exp( p · ln|x| )
(Σ|x-y|^p)^(1/p)   = exp( (1/p) · ln Σ|x-y|^p )
```

工程要点：

- `1/p`（p_reciprocal）在 Host 侧提前算好传下来，别在核内反复做除法（除法指令慢）。
- p=0 走特殊分支：差值非零置 1、零置 0，归约求和 = 非零维度个数。
- ln / exp 在 FP16 下精度损失大 → 见下一节。

## 6. 精度保卫战：FP16 进，FP32 算，FP16 出

- 输入 FP16：先转 FP32 再进计算流水，算完转回 FP16 输出。
- 中间所有累加、ln、exp 全程 FP32。
- 验收线：误差 ≤ 1e-4。精度超标先查三件事：① 是否用 FP16 直接算 ② 累加顺序导致的误差累积 ③ 多核写回是否覆盖。

## 7. 开发三字诀 + 一场实战

1. **跑通**：只做 p=2、小数据、单核；CPU 模式（GDB 单步）跟 PyTorch 对拍，先把算子注册、命名、Json 配置这条「工程链」跑顺。
2. **跑稳**：扩全 p 分支（0/1/2/泛 p）× FP16/FP32 × 四大切分场景；每过一个场景就加进回归测试。
3. **跑快**：msprof_op 采集 PMU → 看流水图找瓶颈 → 按「Tiling 设计 → 流水并行 → 代码细节」三板斧逐个归因验证。
4. **实战**：全量基线表 + 答辩材料（每个优化都能讲出「为什么快、快多少、证据是什么」）。

## 9. 术语速查表

| 术语 | 通俗解释 |
|---|---|
| CANN | 昇腾的计算架构（类比 CUDA 生态） |
| Ascend C | 昇腾算子编程语言（类比 CUDA C++） |
| Host / Device | CPU 侧（管策略）/ NPU 侧（管计算） |
| Kernel | 跑在 AI Core 上的计算函数 |
| Tiling | 数据切分策略（Host 算好传给 Kernel） |
| TilingKey | 切分策略的「档位编号」，Host 与 Kernel 必须一致 |
| GM / UB | 全局内存 / 片上缓存 |
| Double Buffering | 乒乓缓存，搬运与计算并行 |
| Mask | 向量指令的有效位过滤器 |
| Pad | 补齐到 32B 对齐的填充数据 |
| PMU | 硬件性能计数器（类比 Nsight Compute 的硬件 counter） |
| 对拍 (oracle) | 跟 PyTorch 基准逐元素比对验证正确性 |
