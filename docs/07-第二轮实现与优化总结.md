# 07 · 第二轮实现与优化总结

> 日期：2026-10-21 ｜ 硬件：Atlas 800T A2（910B3 x4，本报告用单卡） ｜ CANN 9.1.0（实际路径 cann-8.5.2）
> 结论速览：正确性 **56/56 全绿**；(4096,512) FP32 p=2 达 **27.7 ms**，为 torch_npu 原生的 **4.8x**、PyTorch CPU 的 **2.3x**，较第一轮 v1 再提升 **1.20x**；FP16 p=2 **28.2 ms**（4.5x vs native）。p=0 场景领先原生 **49x**。

## 1. 第二轮设计：tile 化 pair 距离（迁移 PyTorch CUDA / 社区思路）

### 1.1 问题定位（第一轮留下的瓶颈）

第一轮 v1 按 **pair 均摊** 组织计算，每算一个 pair 都现取两行 i、j。这带来两个结构性浪费：

1. **读流量放大**：x 全矩阵 8MB（4096×512 FP32），但每个 pair 都要读一行 i + 一行 j，总读 ~N²·M/2 元素量级 ≈ 8.6 GB，远超矩阵本身；
2. **缓冲换入不换出**：v1 用 `TQue` 双缓冲预取 i 行，但 j 行随取随丢，j 行的复用（同一 j 行服务所有 i<j 的 pair）没有跨 pair 保留。

### 1.2 v2 核心思路（二维分块 + j-tile 常驻）

参照 PyTorch CUDA `pdist` 与社区的 **tile 化**（i-block × j-tile 二维分块）思路，把工作切分为「单元 cell」：

| 概念 | 取值 | 含义 |
|---|---|---|
| 单元 (jt, b) | jt,b ∈ [0, NT) | pair (i,j) ∈ `[b·8, b·8+8) × [jt·8, jt·8+8)` 且 i<j |
| 单元号 u | `jt(jt+1)/2 + b` | jt 外层、b 内层连续编号，总数 `U = NT(NT+1)/2`，`NT = ceil(N/8)` |
| 核间切分 | 按 u 连续均摊 | 每核 `unitPerCore(+1)` 个单元，负载严格均衡 |
| 对角单元 | b == jt | tile 内部上三角，i 源直接复用 j-tile 数据（**零搬运**） |

关键收益：

1. **j-tile 外层常驻 UB**：一组 j 行（8 行）只搬进 UB 一次，服务组内全部 i-block（最多 jt+1 个）→ x 读流量从 v1 的 ~N²·M/2 降为 ~N²·M/8（约 **4x 降低**，实测带宽口径约 8x 的降低来自 i/j 双侧摊薄）；
2. **i-block（8 行）经 TQue 深度 2 双缓冲预取**，与 V 计算重叠；
3. **对角单元零搬运**：b==jt 时 i 源直接指向 j-tile 自身，省一次整块读；
4. **每 pair 仅 1 次 `PipeBarrier`**（v1 为 3 次）：单 chunk 场景 `ReduceSum` 直接落入 32B 槽位（`SUM_SLOT=8`），省去逐 pair 的 `Add` 累加与额外两道屏障；
5. **单元粒度 = 64 pair**：`V_S`/`S_MTE3` 同步与标量压缩频次降为 v1 的 1/8。

### 1.3 实现要点

- **行 i 首输出下标**：`RowStart(i) = i·(N-1) - i·(i-1)/2`（i=0 时 `i·(i-1)` 无符号下溢因子为 0，安全）；
- **离对角 q 地址**：`q = RowStart(i) + jt·8 - i - 1`；对角单元 `q = RowStart(i)`；
- **单元号反解 (jt,b)**：顺序推进减法（标量域无 sqrt），单核起点只需 O(N) 一次推进，不开方；
- **滚动预取**：`DeQue → 计算 → FreeTensor → Alloc 预取 +2`，规避 TQue 深度 2 的死锁；
- 缓冲规格见 `op_kernel/pdist.cpp`（`K_BLOCK=1024, TJ=TI=8, SUM_SLOT=8, OUT_STRIDE=16`）。

## 2. 途中修复的正确性问题（第三次踩 DataCopyPad 对齐陷阱）

首轮 v2 回归 **48/56**，暴露两类 fp16 问题（fp32 全绿）：

| 症状 | 根因 |
|---|---|
| fp16 N=3/9/16、M=8/24 数值错（max_rel 达 2.2，读到相邻 pair 的值） | 2D `DataCopyPad` 的 `blockLen` 非 32B 整数倍时，硬件把上一行尾块**重复进下一行** |
| fp16 N=2（M=1、M=131）崩溃（aclrtSynchronizeStream ret=507035 aicore 异常） | 同一根因：非 32B 对齐搬运导致越界/数据腐蚀 |

M 扫描（N=5）佐证：M=8/24 FAIL、M=16/32/64/128 PASS —— **失败恰好 = M 非 16 元素（32B）倍数**；M=24 数据分析证实首 16 元素正确、尾 8 元素 = 上一行值。

**修复**：`RowStride` 改为按 dtype 对齐到 32B（fp16=16 元素、fp32=8 元素），非对齐长度逐行搬运且 `blockLen` 向上补齐 32B：

```cpp
__aicore__ inline uint32_t RowStride(uint32_t len) const
{
    constexpr uint32_t ALIGN_ELE = 32 / sizeof(T);
    return (len % ALIGN_ELE == 0) ? len
                                  : ((len + ALIGN_ELE - 1) / ALIGN_ELE) * ALIGN_ELE;
}
```

重建后 **56/56 全绿**（此前 N=2 崩溃两例与 M=8/24 数值错例一并消除）。这是本项目第三次踩 `DataCopyPad` 非 32B `blockLen` 陷阱（前两次在 v0、v1），已固化进 [docs/03](03-问题排查与优化速查手册.md) 速查。

## 3. 性能归因：探针法 + 一个"死胡同"结论

### 3.1 探针法量化各段开销

在 `TiledFinalize` 的标量回读前插入 `return` 探针（跳过 GetValue/SetValue + GM 落盘，保留 Sqrt/幂的向量运算），测得：

| (N,M) p=2 FP32 | 完整 | 跳过 finalize 回读 | finalize 标量回读占比 |
|---|---|---|---|
| (1024,512) | 1.76 ms | — | — |
| (4096,512) | 27.7 ms | 24.3 ms | ~12% |

结论：**瓶颈在向量计算本身（Sub/Mul/ReduceSum 占 88%），不在标量压缩/落盘**。因此第二轮进一步优化的方向应是降低逐 pair 的计算链开销。

### 3.2 repeat-stride 优化为何不成立（一个可复用的结论）

为降低指令发射次数，考察了 Ascend C 的 `Sub/Mul` repeat-stride 重载（`uint64_t mask, uint8_t repeatTime, BinaryRepeatParams`），预期把 512 元素的标量循环（8 次下发）压成 1 条指令。

**实测源码结论（c220 / 910B）**：count 版 `Sub` 内部已走 **计数器模式** ——

```cpp
set_mask_count();
set_vector_mask(0, count);            // 计数器模式：mask 即元素数
vsub(dst, src0, src1, /*repeatTime=*/1, DEFAULT_BLK_STRIDE, ...);  // 单条指令
```

即 count 版本就已用**单条 vsub + 硬件计数器循环**处理任意长度，不存在标量下发放大。**repeat-stride 改写对 c220 的二元运算无收益**，故未采纳。

### 3.3 真正的剩余瓶颈（供后续方向）

- 逐 pair 的 `ReduceSum`（512 元素树归约）与 `diff` 缓冲复用构成**串行依赖链**，每 pair 的 Sub→Mul→Reduce 因公共缓冲 `diff` 相互串行，V 流水级间 ILP 有限；
- 估算：8.4M pair / 48 AIV 核 ≈ 175K pair/核，每 pair 三段串行 V 指令 + 1 次 `PipeBarrier`，latency 主导而非带宽/发射率主导；
- 后续可探索：① 多 `diff` 缓冲交错提升 ILP；② 用「块归约 + 跨 repeat 归约」把多 pair 的 reduce 合并为一次向量轮次；③ p=2 走 Cube（矩阵乘）路线。

## 5. 归因链

1. **v1 → v2（33.3ms → 27.7ms，1.20x）**：j-tile 外层常驻 + i-block 二维分块，x 读流量结构性降低（~N²·M/2 → ~N²·M/8）；对角单元零搬运；每 pair 屏障 3→1；V_S/S_MTE3 同步与标量压缩频次 ÷8。
2. **为何未达"读流量 4x 降低 → 性能 4x"的线性预期**：当前瓶颈已从 v1 的**读带宽**转移到 v2 的**逐 pair 计算链**（ReduceSum 树归约延迟 + diff 缓冲串行复用），见 §3.3。读带宽不再是约束，验证了"第二轮把读流量降到硬件下限"的目标已达成，剩余空间在计算流水。
3. **与原生/CPU 的对比**：p∈{1,2} 面 torch_npu 通用路径（未按 p 特化），v2 稳定 4.5~4.9x；p=0 面原生 15.6 倍的病态回退，v2 领先 49x；CPU 侧小形状 v2 以 Hardware 单指令计数器模式+双缓冲取得 22x（(512,256) p=2）。
