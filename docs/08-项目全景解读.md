## 第一部分：这个项目是什么

### 1.1 定位

在昇腾 910B3 上用 **Ascend C** 从零实现并深度优化一个对标 `torch.nn.functional.pdist` 的自定义算子，服务 **华为 ICT 大赛挑战赛**（第十届初赛第 2 题原型，2027-02 初赛）与**昇腾算子赛**双赛道，交付"可上板的高性能算子工程 + 带归因链的实测数据 + 可答辩的技术方案"。

Pdist 本身：输入 N 个 M 维向量（形状 `(N, M)`），输出两两之间的 p-范数距离，共 `N(N-1)/2` 个值，按上三角行主序展开：

```
d(xi, xj) = ( Σ_k |xi_k - xj_k|^p )^(1/p)        p=2 欧氏 / p=1 曼哈顿 / p=0 非零维计数 / 泛 p 走 ln+exp
```

### 1.2 当前成绩速览（全部实测，可复跑）

| 指标 | 数值 | 出处 |
|---|---|---|
| 正确性 | **56/56 全绿**（4 个 p 分支 × FP32/FP16 × 7 组形状） | docs/07 §2 |
| 主场景 (4096,512) FP32 p=2 | **27.7 ms** = torch_npu 原生的 **4.8x**、PyTorch CPU 的 **2.3x** | results/perf_v2_tiled_fp32 |
| p=0 场景 | 42.7 ms = 原生的 **49x**（原生病态 2087 ms） | 同上 |
| FP16 (4096,512) p=2 | 28.2 ms = 原生 **4.5x**，且精度 ±1 ulp 反超原生（原生 p=1 差 0.125） | results/perf_v2_tiled_fp16 |
| 优化历程 | v0 72.3ms → v1 33.3ms → v2 27.7ms（每轮有归因链） | docs/06、docs/07 |

### 1.3 项目的三层意义

**① 竞赛意义**：挑战赛初赛是"方案提交制 + 性能排名"，要求的不只是跑得快，而是**每个优化决策都有实测数据和归因**（为什么快、快多少、证据在哪）。本仓的 `results/` + `docs/06/07` + `docs/05` 答卷骨架就是这条证据链的完整模板。

**② 技术意义**：torch_npu 原生 pdist 存在四条明确短板——(4096,512) 各 p 值耗时同为 ~133ms（通用路径未按 p 特化）、p=0 病态慢 15.6 倍（2087ms）、FP16 精度差（p=1 差 0.125）、绝对性能不足。本项目逐条击穿这四个短板，是一个"找准原生实现软肋 → 针对性设计 → 数据验证"的完整实战案例。

**③ 可复现意义**：pdist 把算子开发的四大基本功——**精度调试、数据切分（Tiling）、多核并行、性能调优**——压缩在一个算子里；而本仓罕见地保留了**完整优化史**（v0→v1→v2 三轮，每轮有数据有归因）、**三次 DataCopyPad 对齐事故的完整排错记录**、**一个被证伪的优化方向（repeat-stride）**和**一套可复跑的验证体系**。

```text
├────────────────────────────────────────────────────────────────────┤
│  Host 层（CPU，管策略）  op_host/                                      │
│  pdist.json(原型) → pdist.cpp(OpDef注册/InferShape/Tiling计算/        │
│  BlockDim/标量预计算 p、1/p、pMode)                                    │
├───────────────── 二进制契约：PdistTilingData（POD）──────────────────┤
│  Kernel 层（NPU，管计算）  op_kernel/                                  │
│  pdist.cpp：KernelPdist<T, P_MODE> 模板                               │
│    v2 主路径(M≤1024)：j-tile 常驻 UB + i-block 双缓冲 + 单元(64pair)   │
│    均摊多核 → Sub/Mul/ReduceSum → finalize 标量压缩 → DataCopyPad 写回 │
│    v1 回退(M>1024)：行分段 + tile×chunk 流水                           │
├────────────────────────────────────────────────────────────────────┤
│  硬件层  910B3：48 AIV 向量核 / UB 192KB/核 / 32B 对齐硬约束 / HBM     │
└────────────────────────────────────────────────────────────────────┘
```

### 2.2 一次调用的完整数据流（端到端调用链）

```text
python tests/run_custom.py --shape 4096,512 --p 2
   │  生成 x.bin（固定种子）
   ▼
pdist_driver (C++)
   │  aclInit → aclrtMalloc → H2D 拷贝 → aclCreateTensor
   ▼
aclnnPdistGetWorkspaceSize  ──► Host: InferShape（Y=N(N-1)/2）
   │                           Host: TilingFunc（pMode/dtypeFlag/单元均摊/
   │                           usedCoreNum/pReciprocal → PdistTilingData）
   ▼
aclnnPdist × iters（每次：下发 kernel 到 48 AIV 核）
   │  每核：按单元号反解 (jt,b) → DataCopyPad 搬 j-tile/i-block →
   │        FP16 先 Cast 到 FP32 → Sub → |d|^p 四分支 → ReduceSum →
   │        Sqrt / ln+exp 开 p 次方 → GetValue/SetValue 标量压缩 → 写回 GM
   ▼
D2H 拷出 y.bin ──► Python 与 CPU 侧 torch F.pdist 逐元素 allclose
                   （fp32: atol=rtol=1e-4；fp16: 对 y_ref.half() 判 atol=1e-3, rtol=2e-3）
```

## 第三部分：指标数据与社区实现的对比、差距归因

### 3.1 本项目自己的纵向对比（优化史即归因史）

(4096,512) FP32，单位 ms，引自 docs/06 §2.3 与 docs/07 §4.1：

| 版本 | 单变量改动 | p=0 | p=1 | p=2 | p=3.7 | vs 原生(p=2) |
|---|---|---|---|---|---|---|
| 原生 torch_npu | — | 2087 | 133 | 133 | 133 | 1x |
| v0 naive | 逐 pair 现搬两行、逐元素写回 | 80.3 | 72.1 | 72.3 | 88.0 | 1.85x |
| v1 generic | 行 i 常驻 UB + j 行批量 8 + 双缓冲 + p 分派/标量下放 | 47.8 | 32.8 | 33.3 | 47.8 | 4.0x |
| **v2 tiled** | **j-tile 常驻 + i-block 二维分块 + 对角零搬运 + 屏障 3→1** | **42.7** | **27.3** | **27.7** | **41.6** | **4.8x** |

读流量口径：v1 ≈ N²·M/2 元素（~17GB），v2 ≈ 每单元一次 i-block + 每 jt 组一次 j-tile（~2.2GB），**结构性降低约 8 倍**（docs/07 按 4x 保守口径、kernel 注释按 8x 口径，本文取实测归因一致的"数量级 4~8x"）。

### 3.2 与社区横向对比

| 实现 | 平台 | (4096,512) FP32 p=2 | 相对本项目 | 关键特征 |
|---|---|---|---|---|
| **本项目 v2** | 昇腾 910B3 | **27.7 ms** | 1x | 向量路径 tile 化，48 AIV |
| torch_npu 原生 | 昇腾 910B3 | 133 ms | 慢 4.8x | 通用路径、不按 p 特化、p=0 病态回退（2087ms） |
| PyTorch CPU | Kunpeng aarch64 | ~62-70 ms | 慢 ~2.3x | CPU 向量化和多线程 |
| PyTorch CUDA pdist | A100（估算） | ~1-3 ms | **快 10~25x** | 2D block tiling + shared memory 行缓存 + warp shuffle 归约 |
| GEMM 展开路线（cuML / 社区 cdist 思路） | A100（估算） | <1 ms | **快 30x+** | L2 展开 ‖a-b‖²=‖a‖²+‖b‖²-2a·b，走 Tensor Core 矩阵乘 |

> CUDA 两行为**估算口径**，依据：总计算量 ≈ 8.4M pair × 512 维 × 3~5 FLOP ≈ 13~21 GFLOP，A100 FP32 峰值 19.5 TFLOPS（Tensor Core FP16 312 TFLOPS），理论下限 ~0.7ms，计入 kernel 结构效率取 1~3ms 量级。本项目 v2 的 tile 思路本身即迁移自 PyTorch CUDA pdist（见 docs/07 §1.2）。

### 3.3 差距原因分析（分三层，全部有出处）

**A. 为什么能赢原生 4.8x / 49x —— 工程红利（已兑现）**

1. 原生对所有 p 走同一条通用路径（各 p 同速 133ms），本项目按 pMode 编译期模板分派：p=2 只走 Sub+Mul，p=0 走 4 条整数位技巧指令，完全不碰 ln/exp（docs/06 §1.2）。
2. 原生 p=0 病态回退 15.6 倍（2087ms），本项目专用分支直接 49x（docs/07 §4）。
3. tile 化 + 双缓冲把读流量降约 8x、DMA 指令数 ÷8、MTE2 搬运与 V 计算重叠（docs/06/07 归因链）。
4. 标量（p、1/p、Tiling）全部 Host 预计算，核内零除法。

**B. 为什么离硬件理论界还有距离 —— 计算延迟主导（项目自证）**

1. v2 读流量 ~2.2GB，按 910B3 HBM 带宽折算理论下限仅 ~2ms 量级，但实测 27.7ms → **带宽早已不是瓶颈**（docs/07 §5.2 明确此结论）。
2. 探针法量化：跳过 finalize 标量回读只省 12%，**88% 时间在 Sub/Mul/ReduceSum 向量计算链本身**（docs/07 §3.1）。
3. 逐 pair 的 `Sub→Mul→ReduceSum` 因共用 `diff` 缓冲构成串行依赖链，V 流水级间 ILP 受限；8.4M pair / 48 核 ≈ 175K pair/核，每 pair 三段串行 V 指令 + 1 次屏障，是 **latency-bound 而非 throughput-bound**（docs/07 §3.3）。
4. 一个已证伪的方向：repeat-stride 改写无收益——c220/910B 的 count 版 Sub 内部已是"单条 vsub + 硬件计数器"模式，不存在指令下发放大（docs/07 §3.2，此结论可复用到所有二元向量运算）。

**C. 为什么离 CUDA 社区还有一个数量级 —— 硬件代差 + 路线未用尽**

1. **向量单元算力代差**：A100 有 108 个 SM 的 FP32 阵列（19.5 TFLOPS）；910B 的 AIV 向量单元 FP32 吞吐与 Cube 单元（FP16 ~320 TFLOPS 量级）差一个数量级以上。v2 有效算力折算仅 ~0.5-0.8 TFLOPS，说明既受限于归约延迟，也受限于向量单元本身的吞吐天花板。
2. **归约原语差异**：CUDA 用 warp shuffle 做 32 线程并行归约（单指令级、延迟极低）；Ascend C 的 `ReduceSum` 是树归约，且与前后向量指令构成依赖链。
3. **路线未用尽（最关键、也是项目自认的下一步）**：p=2 场景社区高性能实现的标配是 **GEMM 展开**——‖a-b‖² = ‖a‖²+‖b‖²−2a·b，把逐 pair 距离变成一次大矩阵乘，从而用上 Cube/Tensor Core（cuML 的 pairwise_distance 即此路线）。本项目目前全路径都在向量单元上，docs/07 §3.3 已把"p=2 走 Cube 路线"列为后续方向。
4. 次要方向（docs/07 §3.3）：多 diff 缓冲交错提 ILP；多 pair 归约合并为一次向量轮次。

**D. 精度维度：本项目反超原生**

原生 FP16 全程半精度计算，(256,128) p=1 误差达 0.125；本项目"FP16 进 → FP32 算 → FP16 出"，与 FP32 oracle 对齐到 ±1 ulp（docs/04 §2、docs/07 §4.2）。代价是 FP16 比 FP32 略慢（28.2 vs 27.7ms，多一次整块 Cast）——数据诚实可见。

### 3.4 小结：这个项目在社区坐标系中的位置

- **对 torch_npu 原生**：全面压制（4.5~49x + 精度反超），证明了"原生通用路径"的优化空间，达成了赛题"按性能排名"的核心主张。
- **对社区最佳实践**：已迁移 CUDA tile 化思想并吃透，但尚未走 GEMM/Cube 路线，距离 CUDA 高性能实现约一个数量级——差距来源是硬件路线选择而非工程失误，且补齐路径已在文档中明确。这恰好给学习者留了一个"看得见的下一级台阶"。
